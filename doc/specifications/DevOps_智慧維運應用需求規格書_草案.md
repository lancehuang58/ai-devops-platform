## SRS-01 目標與成功條件

建立常駐 Teams 的單一對外 DevOps Bot。平台接收既有監控（Prometheus、既有 API endpoint）的事件，去重後自動開案與建立 Jira，主動收集資料並調查是否有固定解法；沒有固定解法時提出解法，經人員核准後套用、驗證，再由使用者確認結案草稿後結案，並把經驗沉澱為知識（已對齊需求 §1.1、§4）。

變更只能由兩種來源授權：任一已驗證使用者一次核准完整計畫，或命中團隊預先定義的自動修復白名單（U9、U13）。核准沒人回應時維持 PENDING（U10）。每個工作項目的過程、證據、核准、執行與結果都可稽核；平台 DB 是權威紀錄，Jira 是可補送的外部投影。公司 Qwen 為主要模型；複雜調查預留受控外部模型與外部 Agent 接入。

「Jenkins Job 內容查詢」與「備份後刪除單一 Job」仍是平台的兩個參考方案，用來驗證唯讀查詢與固定變更的完整控制；它們不代表整個平台需求已交付。

## SRS-02 工作項目類型與服務範圍

所有工作項目共用一張 `work_item` 主表與一套 `WorkItemStatus`（已對齊需求 §2、§3，U7）：

| item_type | 內容 | 典型來源 |
|---|---|---|
| `INCIDENT` | 系統異常、設定錯誤、服務失效、效能異常等 | 監控事件自動開案；使用者回報；INQUIRY 發現異常後轉型 |
| `REQUIREMENT` | 建立或修改系統需求，含標準申請（Jenkins pipeline、DB table、測試 DB user）與計畫性變更 | 使用者在 Teams／Web 提出 |
| `DISCUSSION` | 需要分析、比較方案、做決策，不必然變更系統 | 使用者發起 |
| `INQUIRY` | 使用者要求平台主動檢查或回答問題 | 使用者發起（U3） |

需求以目標流程描述，不再分「現行 v1／下一期」（U8）：收集資料 → 調查是否有固定解法 → 否則提出解法 → 解法過審（或命中白名單）→ 套用解法 → 驗證 → 結案草稿確認 → 結案。交付排程由開發計畫管理，不寫進需求。

| 工作方式 | AI 責任 | 平台責任 |
|---|---|---|
| 調查與診斷 | 選擇已發布唯讀工具、分析證據、提出假設與建議 | 先檢索知識、限制工具／資料／時間、驗證來源；工具技術故障停止該次調查 |
| 固定解法 | 提出已發布 solution／申請模板候選及適用依據 | 驗證前提、產生變更預覽、使用者核准或白名單、固定步驟及 VERIFY |
| 新解法 | 擬定解法草稿；可執行步驟只能引用已發布命令 | 核准綁定計畫 hash；未發布命令只能列為人工步驟（`MANUAL_ACTION`） |

本版服務目錄包含 PostgreSQL、MariaDB、Jenkins、GitLab、Jira、Confluence、Nexus、Harbor、Graylog、Rancher、VM management、Grafana 等；各服務能力依方案逐步接入，未接入者標示 disabled，不視為平台故障。架構保持模組化單體，不以 Kafka／RabbitMQ／Redis 為前提。

不在範圍：使用者自建 bot、多 bot 協作、bot registry／`bot_id`（U12）；角色／權限分級（U13）；AI 自行發布正式知識或可執行方案。

## SRS-03 使用者與身分

| 身分 | 允許 | 邊界 |
|---|---|---|
| 已驗證使用者 | 查詢、調查、建立工作項目、提交與核准提案（含自行核准，畫面標示「自行核准」）、確認事件候選與結案草稿、檢視 raw evidence、維護方案／規則／監控來源設定、設定與解除 kill switch、啟動外部模型 grant、審查發布知識 | 每個動作都寫稽核；仍受已發布能力、有效前提、kill switch、resource_hold 與資料政策限制 |
| AI／執行器 | 在工作項目的授權（使用者核准或白名單規則）內執行被允許的步驟 | 模型輸出不是授權；不可自我核准 |
| 外部模型／外部 Agent | 經資料政策與案件 grant 允許的調查、證據讀取與提案 | 無 CHANGE、核准、raw、秘密或其他對話權限 |
| 紀錄同步服務身分 | 依紀錄政策更新本案 Jira／文件目的地 | 只可寫安全紀錄及依映射轉換 Jira workflow；不取得受管服務變更權 |
| 監控來源 | 以通道適配器送入告警事件 | 只能產生事件；webhook 需驗證，不合法訊息進無效訊息紀錄 |

目前不區分角色（U13）：LDAP 驗證公司帳號，Teams 身分須可信連結公司帳號；只有一種已驗證使用者。顯示名稱、聊天文字、卡片內容及外部模型聲稱都不能代替身分。核准與派送時重新驗證身分與計畫內容。原本 ADMIN-only 的動作改為所有已驗證使用者可操作，但每次都寫稽核（已對齊需求 §12.2）。未來若要加回角色，以「動作權限清單＋principal 對應」加入，不改狀態機與資料表。

## SRS-04 功能需求

| 編號 | 需求與預期結果 |
|---|---|
| FR-01 | 自然語言受理、目標解析及補充必要資料；不猜環境、資源或執行範圍。 |
| FR-02 | 調查可以分析未知問題並提出解法。可執行的步驟只能引用已發布命令與參數 schema，未發布命令只能列為人工步驟；模型不能臨場生成任意 SQL／shell／API 呼叫。 |
| FR-03 | config 不足時可自主使用已發布 QUERY 取得 Jenkinsfile、函式庫、log 或相關服務資料；引用來源、時間與版本。 |
| FR-04 | 任一已驗證使用者一次核准完整具體計畫，綁定目標、參數、Runbook／命令版本、證據與計畫 hash；申請人可自行核准並標示（U22）。核准沒人回應時維持 PENDING，不自動拒絕、不逾時、不升級（U10），每個工作日 09:30 提醒一次（U21）。核准當下重新驗證計畫 hash 與目標基準，基準已變則提案作廢、回到提出解法；變更內容後須重新核准。 |
| FR-05 | 正常變更後以既定 VERIFY 檢查效果；區分成功、失敗、部分完成、未知、略過及拒絕。 |
| FR-06 | 保存可定位問題的調查表與證據，包括 VM、IP、hostname、service、related service、根因、錯誤類型、detail、memo、build、版本、時間線、方案、核准與驗證。未知及不適用值明示。 |
| FR-07 | 資源使用穩定 ID；支援多 VM／多服務／多環境及關聯，不以名稱或 IP 當授權身分。 |
| FR-08 | 帳密、token、對話及組織指定敏感內容不進模型／共用報告。原始服務證據與可分享投影分開；所有已驗證使用者可在 Web 受控頁面檢視 raw，每次存取都稽核；Teams 與 Jira 只顯示安全投影；秘密在任何情況都不顯示（U28）。 |
| FR-09 | 依工作必要依賴與健康狀態判定是否可派送；歷史 build FAILURE 不等於連線故障。 |
| FR-10 | 維運 CHANGE 故障不重送、換通道、補跑、回滾或補償。已送 CHANGE 回應逾時，僅在核心與查詢通道正常且已有查核定義時，允許一次唯讀查核；不接續後續變更。紀錄補送另依 FR-31。 |
| FR-11 | Teams 重送、重複核准、重啟與同目標競態不造成重複變更；未知結果不得推定未生效。 |
| FR-12 | 產生有證據、方案版本、核准及缺口的案件報告；故障或 Qwen 不可用時只以已存資料產生固定摘要。 |
| FR-13 | 人員維護並測試發布能力、Runbook、命令、資源、健康條件、監控來源與自動修復規則；草稿與停用版不可執行；所有設定版本化並稽核。 |
| FR-14 | 排障由程式保證先檢索正式知識與可見歷史案件，再讓模型調查；文件命令不直接成為執行權。 |
| FR-15 | 監控事件與 INCIDENT、REQUIREMENT、DISCUSSION 開案時自動建立 Jira，不逐案詢問（U6）；INQUIRY 預設只存平台，轉型為 INCIDENT 或勾選「需要追蹤」時才建 Jira（U20）。Confluence 每案報告為可選目的地，可由紀錄政策關閉，知識以 GitLab 為準（U25）。 |
| FR-16 | Teams 支援對話、表單、核准、事件候選確認、結案草稿確認與進度。正常排程依已發布設定啟用，漏跑不補。 |
| FR-17 | 模型品質評估與回歸保持獨立模組；Qwen 為必要基準，外部模型及檢索比較以獨立 profile 報告，不混用成績。 |
| FR-18 | 方案與工具測試保持獨立模組，固定模型答案驗證正式平台控制；離線與真實隔離服務驗證分列。 |
| FR-19 | 支援單一 Freestyle／一般 Pipeline 備份刪除；排除 Folder、Multibranch／分支、批次及萬用字元。 |
| FR-20 | 刪除以 config 提交後讀回核對、設定一致及無執行／排隊為門檻；MCP 刪除一次，正常 ACK 後固定驗證。 |
| FR-21 | Job config 備份預設 90 天，可配置；UNKNOWN／待人工未結案受保護，清理留稽核。 |
| FR-22 | Job 問答免逐工具核准，可在 building／queued 時查詢；禁止為理解內容而執行腳本或觸發 build。 |
| FR-23 | Teams 入口驗證租戶、來源、公司帳號及活動去重；跨入口可關聯案件，但不能存取他人的對話。 |
| FR-24 | 已驗證使用者可提交已開放的 pipeline、DB table、測試 DB user 標準申請、補資料及查進度；固定模板產生具體預覽，經任一已驗證使用者核准後才執行。任意命令不屬標準申請。 |
| FR-25 | 外部模型接入納入需求；供應商及資料政策核准後，由使用者每案檢視目的及預計外傳資料並明確啟動 grant。Qwen 仍為主要模型，不以技術故障自動 fallback；使用者逐案、平台外的商用模型人工接管見 FR-47～50。 |
| FR-26 | 提供案件摘要、證據清單／安全內容、知識檢索、受控診斷、提案及狀態 API 契約；外部 Agent 經相同政策，不直連內部管理服務。 |
| FR-27 | 正式知識、歷史案件、即時觀測分開保存與引用；相似案例不代表本次根因成立。 |
| FR-28 | 結案草稿勾選的項目可產生知識／Runbook 待審草稿，經查重、人員審查、測試及發布才成正式知識或可執行流程。 |
| FR-29 | 檢索支援精確關鍵字與 metadata，預留語意與混合檢索；回傳來源、版本、日期及完整前提關聯。embedding 能力需獨立確認。 |
| FR-30 | 平台管理穩定 knowledge_id／item_id；文件平台只存對照 ID，保留原文與結構化匯出，支援預計兩年內替換 Confluence。 |
| FR-31 | 操作與紀錄結果分開。每次 Jira 寫入先在同一業務交易存入 DB 同步請求；首次失敗後最多補送 5 次（間隔 1m／5m／15m／1h／4h＋20% jitter，不設總期限），仍失敗即停止並轉人工（U5、U24）。結果不明先以 case marker 查核，不重複建單；401／403、schema 錯誤、內容衝突直接轉人工。外部同步故障不阻擋開案、調查、核准與已核准維運。 |
| FR-32 | 外部模型交接包含已允許的問題、版本、證據、已排除原因、已嘗試動作、假設與調查 scope；保存可驗證摘要，不要求模型內部思考過程。 |
| FR-33 | 依已配置並驗證的 WorkItemStatus→Jira 狀態／transition 映射自動同步（已對齊需求 §10.4）；人工狀態衝突轉人工，Jira 變化不得反向觸發維運。 |
| FR-34 | 監控接入：Prometheus Alertmanager webhook、PromQL 定期查詢、既有 API／health endpoint probe 為一級事件來源；特殊入口以 Connector 擴充（U1、U2）。來源本身失聯產生 `MONITOR_SOURCE_UNAVAILABLE` 事件，不當成受管服務故障。 |
| FR-35 | 標準告警事件與去重：依 `(source_id, source_event_id)` 冪等接收；依 fingerprint 聚合為告警群組，同一 fingerprint 同時只有一個未結群組、只開一案（設計文件 B）。 |
| FR-36 | 故障後持續監控、不持續告警（U4）：唯讀監控照常（interval < 60 秒時放寬到 60 秒，U23），重複事件只累計次數；恢復時只通知一次。抖動、重開窗依 U17；嚴重度升高通知一次並更新 Jira 優先級（U29）；維護時段只記錄不開案（U27）。 |
| FR-37 | 跨資源關聯（U18）：關聯範圍內的告警先整合成一則通知，不開單、不開 Jira；任一已驗證使用者確認是同一事件後才開一張單；系統只在規則 `auto_confirm=true` 且證據 E1～E3 成立時自動確認（U30）；沒人確認維持待確認並每 30 分鐘提醒（U31）；確認前全部恢復則 DISMISSED（U33）。 |
| FR-38 | 主動調查（U3）：使用者可要求平台檢查指定服務；調查中發現異常時轉型為 INCIDENT 並走同一去重。 |
| FR-39 | 自動修復白名單（U9、U16）：只有命中已發布 solution 且符合啟用中規則條件、頻率限制（每群組 1 次、同資源 24 小時 3 次）、kill switch 與派送前檢查時可免核准執行；失敗、PARTIAL、UNKNOWN 轉人工，不重試。 |
| FR-40 | 結案草稿（U11）：驗證通過或決定結案時產生結案草稿，使用者確認後才結案；沒人確認維持待結案並提醒（U21）；Qwen 不可用時以固定模板產生草稿。 |
| FR-41 | Kill switch（U15、U26）：任何已驗證使用者可一鍵啟動全域、目標或僅自動修復的停止，並填理由；解除需填理由，系統自動設定的 hold 須核心恢復 READY 後才可解除；解除不重排被擋下的舊計畫。緊急時不設略過核准通道，平台外手動處理後登錄 `MANUAL_ACTION`。 |
| FR-42 | Qwen 不可用（U14）：只暫停 AI 分析、提案與摘要（標 `LLM_UNAVAILABLE`，恢復後續做）；偵測、去重、開案、Jira、唯讀監控、已核准計畫與白名單自動修復照常。 |
| FR-43 | Web 登入與清單（U35）：已驗證使用者以公司帳號密碼登入 Web；預設看到所有進行中的工作項目及目前 WorkItemStatus／`blocked_reason`；可依系統（服務標籤，含任一、未分類、確認無服務）、時間區間（建立或最後更新，Asia/Taipei）、狀態多選篩選並分頁；不分角色（已對齊需求 §17.2）。 |
| FR-44 | Web 明細（U35）：點選工作項目看到基本資料、告警內容、調查資料、解法與執行結果、核准紀錄、結案草稿、資源鎖狀態及合併 case_event／work_activity 的時間軸；raw 與秘密依 U28 受控（已對齊需求 §17.3）。 |
| FR-45 | 並行推進（U37）：多個工作項目同時推進，worker 數量可配置；等待核准、補資料、Qwen 回應、結案確認、資源鎖或 VERIFY 取樣間隔時保存狀態並釋放 worker；同一工作項目同時只有一個步驟在處理（已對齊需求 §19.1～19.2）。 |
| FR-46 | 資源鎖（U38）：同一目標資源同時只允許一個工作項目在 APPLYING／VERIFYING 持有變更權，其他資源不受影響；後到者標 `RESOURCE_LOCK_WAIT` 依序排隊，取得後重做派送前檢查；等待逾上限轉 PENDING_HUMAN；可能仍有在途命令的失效鎖轉 resource_hold，不自動放行（已對齊需求 §19.3～19.5）。 |
| FR-47 | 商用模型人工接管（U39）：使用者可在 Web 明細頁或 API 對任何非 CLOSED 工作項目手動接管，必填工具、模型與原因；平台記錄接管者、時間、工具與模型（`work_activity` kind=TAKEOVER），經 T27 轉 PENDING_HUMAN，取消排隊中的 AI 工作；可能已派送的命令不中斷、鎖依 FR-46 規則處理；Qwen 恢復不自動接回；平台不自動接管（已對齊需求 §20.2～20.3）。 |
| FR-48 | 接管包（U40）：伺服器端組裝並遮罩告警、調查證據、狀態與歷程、已提出的解法、相關白名單與規則，輸出版本化 zip 與 manifest；遮罩依已對齊需求 §20.4 規則，元件失效即拒絕產生；使用外部模型 grant（目的 MANUAL_TAKEOVER）；產生與每次下載都稽核（已對齊需求 §20.4）。 |
| FR-49 | 寫回（U41）：已登入使用者以 Web／API 寫回摘要、根因、已執行處置（標 PLATFORM／OFF_PLATFORM）與驗證證據；內容先經 SecretFilter，存成低信任證據；OFF_PLATFORM 動作須勾選由操作者負責並寫 MANUAL_ACTION；接管中經平台執行的修改仍走核准、資源鎖與 kill switch（已對齊需求 §20.5～20.6）。 |
| FR-50 | 強制結案（U41）：接管中、已有寫回、且沒有可能已派送未終態的執行時，使用者可經 T28 直接結案，`closure_reason=FORCED_BY_COMMERCIAL_MODEL`，不經 CLOSURE_REVIEW；以寫回產生並鎖定結案草稿；不清除 resource_hold／kill switch；Jira 照常同步（已對齊需求 §20.7）。 |
| FR-51 | GitLab 登入（U43）：platform Web 以公司自建 GitLab 的 OIDC authorization code 登入，scopes 為 `openid profile email`，GitLab base URL 與 client id／secret 來自設定。不把 GitLab 群組當角色；任何通過驗證的使用者看到相同內容。深連結在登入後回到原請求。測試使用 mock OIDC，不連真 GitLab（已對齊需求 §21.1）。 |
| FR-52 | 服務目錄（U44）：受管服務與整合服務以 YAML 的型別化 `@ConfigurationProperties` 定義。秘密只允許 `${NAME}` 環境參考。啟動時拒絕缺欄位、解不出來的參考、未知 template type、未知 probe、重複 id 與字面秘密；日誌與錯誤訊息不含秘密值（已對齊需求 §21.2）。 |
| FR-53 | 監控模板與探測鏈（U45）：模板提供預設探測、間隔與門檻；實例提供 id、type、environment、URL、憑證參考與覆寫。順序固定 endpoint → MCP → API → VM（Glove）。只有通道本身失敗才降級；通道回報不健康立刻開案；全部通道失敗才判定 down／unknown，單上帶每一層原因；較高通道失敗但較低通道健康時只發不重複的通道降級通知、不開事故單。結果記錄通道與 fallback 原因，並進入既有標準告警去重（source `probe`）。此順序不適用於變更執行（已對齊需求 §21.3）。 |
| FR-54 | AI 對話（U46）：platform 登入後提供 `/chat`，Thymeleaf＋本地 htmx，session 最多保存 20 回合，可清除。訊息上限 4000 字；純文字跳脫輸出；同源 POST 需要 CSRF。預設停用外部連線，明確啟用後才建立模型與 MCP。 |
| FR-55 | 需求分析（U47）：classpath 或設定位置載入 SKILL.md，先分類 incident／requirement／discussion、辨識目錄資源、規劃唯讀補查，再根據證據回覆診斷、未知事項與下一步；缺少目標時追問。模型故障不宣稱已查詢或已修復。 |
| FR-56 | 模型與工具（U48）：Spring AI OpenAI 相容介面連 Qwen／LiteLLM；模型、base URL、API key 可設定；API key 與遠端 MCP token 僅接受原始 `${NAME}` 參考，啟動解析並遮罩。保留預設 `qwen-flash 3.8`，該精確 id 未獲官方文件證實。MCP 僅限目錄安全設定、過往監控狀態與目錄健康端點 GET；拒絕任意 URL／shell。新增遠端 Streamable HTTP MCP 透過管理者設定唯讀 binding，不能由模型挑選伺服器或原始工具名。對話不執行修復，既有白名單、核准與資源鎖政策繼續適用。 |

| CON-02 | 公司模型無流量配額，URL／key 於開發階段提供；有限 Context、deadline、並行與步數限制持續適用。外部供應商費用／配額另定。 |

| CON-08 | 原始秘密不進聊天、提示、知識、報告或記錄管線。測試 DB user 的秘密交付／到期處理契約未定案前，不發布建立帳號能力。 |
| CON-09 | 技術選型（U36、U43）：Spring Boot 生態系；PostgreSQL＋Flyway；Spring Data JPA；platform 使用 Spring Security OAuth2 Client（GitLab OIDC）＋伺服器端 session，demo 仍為表單登入；Thymeleaf＋htmx 與 App 同一部署；不引入 Kafka／RabbitMQ／Redis 或 SPA（已對齊需求 §18、§21.1）。 |
| CON-10 | 商用模型只用個人訂閱方案（U42）：不用 API key，平台不經 LiteLLM 呼叫商用模型，也不發給 CLI 回呼用的機器 token；由人在自己的機器、自己的帳號操作；不得做成無人值守後端；受用量上限限制；導入前須重新確認供應商條款與公司資料政策（已對齊需求 §20.1、Q27）。 |

## SRS-06 非功能需求

| 編號 | 要求 |
|---|---|
| NFR-01 安全 | 身分、scope、核准、敏感資料與執行資格均由後端強制檢查；低信任內容（log、告警 annotation、工具回應）不能修改政策。 |
| NFR-02 可追溯 | work_item、activity、operation、plan、approval、evidence、knowledge、report、告警群組／事件候選及外部 ID 可關聯；舊結果不可覆寫成新事實。 |
| NFR-03 故障語意 | 技術錯誤、已知業務失敗、缺知識與遠端未知效果分開；不假造成功或根因。 |
| NFR-04 擴充 | 模組化單體，共用控制與 provider／repository／connector 介面；新增監控來源只加 adapter 與 normalizer；不新增多 Bot 或訊息中介。 |
| NFR-05 保存 | DB／證據／知識原文／映射可備份還原；還原不得觸發舊命令重送。保存期限依已對齊需求 §14 NFR-A8；Job config 備份 90 天規則不變。 |

| NFR-07 品質 | 零未授權變更、零秘密外洩、零重複 CHANGE、零未知誤報成功、同一 fingerprint 未結期間重複開案為零；NOT_RUN／BLOCKED_ENV 不算通過。 |
| NFR-08 可攜性 | 文件平台遷移可保留知識版本、來源、存取規則與案件關聯；索引可重建，不能成唯一原文。 |
| NFR-09 可觀測 | 分開顯示操作狀態、記錄完整度、知識索引新鮮度、外部協助狀態、待核准／待結案等待時間與監控來源健康，避免綠燈掩蓋待補紀錄。 |
| NFR-10 可用性與復原 | 接收端 99.5%／月；RPO 15 分鐘、RTO 4 小時（已對齊需求 §14 NFR-A5、A9）。 |
| NFR-11 Web 與並行 | 建議值（待確認 Q26）：work_item 10 萬筆時清單 P95 ≤ 1 秒、明細首屏 P95 ≤ 2 秒；Qwen、Jira 故障不影響 Web 查閱；等待中的工作項目不佔 worker（已對齊需求 §14 NFR-A11、A12）。 |

| AC-31 | 未登入的深連結經 mock GitLab OIDC（scopes 含 openid、profile、email）後回到原請求；GitLab 群組不會變成角色；登入頁沒有密碼欄。不連真 GitLab。 |
| AC-32 | 範例服務目錄在秘密參考都解得出來時可以啟動，文字形式不含秘密值；字面秘密、未知 template type、未知 probe、重複 id 或解不出來的 `${NAME}` 讓啟動失敗，訊息含參考名稱、不含秘密值。 |
| AC-33 | endpoint 回報不健康時立刻開一張 source 為 `probe` 的單，不再呼叫較低通道；同一指紋的下一次探測只累計次數。endpoint 通道失敗而較低通道健康時不開單，通道降級通知只留一筆。全部設定通道失敗時開一張單，摘要含每一層原因，並寫入 probe_result 與 work_activity。 |
