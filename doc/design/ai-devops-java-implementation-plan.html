一、核心設計結論

系統應採「雙模型＋確定性安全引擎」，而不是讓兩個大模型互相投票。兩個模型都可能產生幻覺，只有可重現的查詢、規則、測試及即時系統狀態能成為最終驗證依據。

LOCAL MODEL

自架 Qwen

分類、摘要、格式化、既有 Runbook 對應、Log 群組命名及低風險唯讀工具使用。

REASONING MODEL

商用高推理模型

未知事故、跨服務因果分析、多個互斥假設、風險權衡及多步處置規劃。

DETERMINISTIC

確定性安全引擎

統計、資料查詢、Schema 檢查、Policy、dry-run、執行後檢查、回滾及限流。

HUMAN CONTROL

人員控制

高風險批准、模型手動切換、緊急停止、例外處理及事故指揮。

重要界線：Qwen 可以協助產生「驗證步驟」，但驗證結果必須由程式執行 PromQL、SQL、OpenSearch 查詢、Kubernetes API 或健康檢查後判定；不能由 Qwen 自己宣告驗證成功。

自動或手動切換模型的條件

技術失敗

  • Timeout、HTTP 429／5xx
  • 供應商 circuit breaker 開啟
  • 回傳非預期格式或無法解析
  • 模型服務健康檢查失敗

品質失敗

  • 引用不存在的 Evidence ID
  • 與確定性數據矛盾
  • 低於信心或完整度門檻
  • 重複工具呼叫且沒有進展

操作失敗

  • 人員按下「切換模型」
  • dry-run 或 precondition 失敗
  • 執行後 SLO 惡化
  • 自動回滾後升級高模型／人工
切換規則：唯讀調查可以在保存 Evidence Package 後直接換模型；只要已產生待執行計畫或正式環境正在變更，就先暫停工作流程，新模型必須重新產生 ActionPlan、重新通過 OPA，必要時重新取得人工批准。

模型無關的案件交接包

InvestigationPackage {
  caseId, serviceId, severity, dataClassification,
  alertSummary, metricFacts[], logClusters[], traceExemplars[],
  serviceGraphSnapshot, changeTimeline[], retrievedRunbooks[],
  evidenceLedger[{ evidenceId, source, query, timestamp, hash }],
  hypotheses[], actionsAlreadyTaken[], validationResults[],
  policyConstraints[], prohibitedActions[], requiredOutputSchema
}

不要把供應商專屬聊天紀錄當成案件狀態。切換模型時只提供可稽核的事實、必要摘要及已執行動作，避免把前一個模型的錯誤推理當成事實傳遞。

五、需要自行開發的專用功能

現成軟體可以提供資料、工作流程與執行能力，但「如何判斷、如何切換模型、哪些動作安全」屬於公司的維運知識，必須自行開發。

P0

事件正規化與證據帳本

統一不同告警格式；每項事實保存查詢、時間、來源、hash、權限與 Evidence ID，所有模型結論必須引用。

P0

Model Router & Handoff

依任務、風險、資料分級、能力、成本與健康度路由；支援案件中途自動／手動切換及完整交接。

P0

輸出品質閘門

JSON Schema、必填欄位、Evidence ID、矛盾檢查、重複迴圈、工具參數及信心門檻。

P0

Data Egress Gateway

商用模型呼叫前做資料分類、欄位白名單、秘密／個資遮蔽、內容最小化、Token 上限與完整稽核。

P0

Action Gateway

模型只能提交型別化 ActionPlan；閘道負責 Policy、批准、dry-run、互斥鎖、執行、驗證、取消與回滾。

P0

Tool Adapter SDK

所有工具實作一致的 discover、plan、dryRun、execute、verify、rollback、cancel 介面及冪等鍵。

P1

固定分析引擎

SLO、rolling median/MAD、EWMA、季節基線、容量回歸、部署前後比較，不以 LLM 進行數學計算。

P1

調查與批准 UI

顯示證據、模型、成本、假設、計畫、Policy 結果；提供切換模型、批准、拒絕、暫停及 Red Button。

P1

評估與回歸框架

以歷史事故 Golden Dataset 重播，評估根因、證據、計畫、安全、成本、延遲及模型切換結果。

六、外部 API 與工具合約

REST／OpenAPI 給人員與外部系統；Kafka／AsyncAPI 給事件；MCP 只作為 AI 可發現工具的標準介面。MCP 不取代 Action Gateway 的安全控制。

POST/api/v1/events
送入部署、配置、雲端或自訂事件；必須支援 Idempotency-Key。
POST/api/v1/investigations
建立調查並指定 service、severity、起始 evidence。
GET/api/v1/investigations/{id}
取得狀態、證據、模型、假設、Token／成本與目前計畫。
POST/api/v1/investigations/{id}/model-handoffs
手動指定 Qwen、商用 Provider 或人工接管並填寫原因。
POST/api/v1/investigations/{id}/pause
暫停工具呼叫及模型迴圈，不中止案件資料。
GET/api/v1/investigations/{id}/events
以 SSE 提供調查、切換、批准與執行進度。
POST/api/v1/action-plans/{id}/approve
帶入批准人、範圍、有效期及附加限制。
POST/api/v1/action-plans/{id}/execute
提交執行；伺服器再次檢查版本、Policy 與 preconditions。
POST/api/v1/actions/{id}/cancel
停止尚未完成的工作並依狀態判斷是否回滾。
POST/api/v1/emergency-stop
需要高權限與強驗證；停止新動作並暫停進行中流程。

統一 Tool Adapter 介面

interface OpsToolAdapter {
  ToolDescriptor describe();
  PlanResult plan(ActionIntent intent, EvidencePackage evidence);
  DryRunResult dryRun(TypedAction action);
  ExecutionRef execute(TypedAction action, IdempotencyKey key);
  VerificationResult verify(ExecutionRef execution);
  RollbackResult rollback(ExecutionRef execution);
  CancelResult cancel(ExecutionRef execution);
}

每個工具必須宣告 readOnly、destructive、idempotent、支援環境、最大影響範圍、必要批准等級、前置條件及回滾能力。可用 Spring AI MCP Server 將唯讀工具公開給模型，但 write tool 仍要轉入 Action Gateway。

建議事件 Topic

ops.alert.received.v1、ops.change.detected.v1、ops.anomaly.detected.v1、ops.investigation.started.v1、ops.model.handoff.v1、ops.action.proposed.v1、ops.action.approved.v1、ops.action.executed.v1、ops.action.verified.v1、ops.action.rolledback.v1

API 基本規則：所有寫入 API 都使用 OAuth2、Idempotency-Key、Correlation-ID、樂觀鎖版本及完整 audit；Webhook 使用簽章、timestamp 與 replay protection；API 版本採 URI major version，事件採 schema version。

逐項開放低風險自主處置

出口條件

每個 L3 動作都有 owner、SLO、成功率、回滾率、季度審查及一鍵撤銷權限。

架構原則

  • 先採 Spring Modulith，避免一開始拆成過多微服務
  • Domain 不直接依賴任何模型或工具 SDK
  • 所有 Provider／工具透過 ports-and-adapters
  • 寫入動作採 outbox、冪等鍵與樂觀鎖
  • 每個模型 Provider 有獨立 circuit breaker 與 bulkhead

Model Router 建議決策欄位

taskType、requiredCapabilities、riskLevel、dataClassification、noveltyScore、evidenceCompleteness、latencyBudget、costBudget、providerHealth、operatorOverride。

Provider abstraction：Spring AI 提供跨模型 API 與 Structured Output，但公司的 Model Router、失敗分類、交接包、資料出境政策與升級規則仍應由自有 Java domain 控制，不能完全依賴框架的預設 fallback。

九、必要驗收與故障測試

模型切換

  • Qwen timeout 後接管
  • 商用 Provider 429 後換備援
  • 錯誤 JSON／Evidence ID 被拒絕
  • 人工切換不遺失案件狀態
  • 切換不重複執行工具

安全與資料

  • 秘密及個資不送商用模型
  • Prompt Injection 不能改變 Policy
  • 模型無權取得原始憑證
  • 過期批准不能執行
  • Red Button 能阻止新動作

動作生命週期

  • dry-run 與實際參數一致
  • 重送請求保持冪等
  • precondition 改變即拒絕
  • postcondition 失敗會回滾
  • 回滾失敗立即人工升級

資料與證據

  • 所有結論可回到來源查詢
  • 查詢含時間、hash 與權限
  • Telemetry 缺失會降低信心
  • 舊 Runbook 不會當成最新事實
  • 跨服務時間同步可驗證

耐久性

  • Java 服務重啟可恢復案件
  • Temporal Worker 中斷不丟狀態
  • Kafka 重播不產生重複 Action
  • 外部工具短暫失敗可安全重試
  • 長時間批准等待不占用執行緒

品質與回歸

  • 歷史事故 Golden Dataset
  • 模型／Prompt 版本比較
  • 根因、證據、計畫分開評分
  • 成本與延遲納入評估
  • 未通過門檻不得升級 L3

十、前四週可立即執行的工作

  1. 確認自架 Qwen 的型號、上下文長度、vLLM／其他 serving 方式、OpenAI API 相容程度及工具呼叫能力。
  2. 選定第一家與備援商用模型 Provider，確認 API、資料保存政策、區域、合約及流量限制。
  3. 盤點現有 Prometheus、Grafana、Elastic／OpenSearch、Kubernetes、CI-CD、Ansible 與工單系統。
  4. 挑選 5～10 個 Pilot 服務，建立 owner、SLO、依賴、Runbook、資料分級及三個低風險動作。
  5. 建立 Java Spring Modulith repository、核心 Domain、OpenAPI、Keycloak、PostgreSQL 與 OTel Java Agent。
  6. 實作第一個只讀 Alertmanager Webhook → Incident → Evidence → Qwen 摘要流程，全程禁止任何 write tool。
第一個成功里程碑：收到一筆正式告警後，平台能建立案件、找到正確服務與 Owner、查詢關聯 metrics／logs／traces／部署、由 Qwen 產生附 Evidence ID 的摘要；人員可按下「升級商用模型」，由新模型在相同案件上繼續分析。
